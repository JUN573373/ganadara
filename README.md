#  발주체크 웹 도구

GitHub Pages에서 기관 로그인·발주 스크래핑과 발주체크표 정리·편집·다운로드를 제공하는 것을 목표로 하는 프로젝트입니다. 브라우저 직접 수집 가능 여부는 사용자가 확인합니다. 허가된 사용자만 이용하며 각자 본인의 기관 계정을 연결한다는 요구사항을 유지합니다.

**1차 개발:** 일반·다크모드 화면, 기관별 계정 입력, 조회 조건, 브라우저 수집 코드, 실시간 로그, 중지와 원본 형식 엑셀 다운로드를 구현했습니다. 실제 기관 로그인·CORS·쿠키 호환성은 사용자가 확인하며, 이번 개발 검증은 가상 기관 응답으로 수행했습니다. 발주체크표 편집·변환과 서비스 접근 제한은 후속 범위입니다.

## 1. 필수 요구사항과 실행 구조

**GitHub Pages만 사용하는 방향으로 진행하며, GitHub Actions 사용 계획은 철회합니다.**

- 사용자는 EXE 없이 웹에서 기관 계정 연결·발주 수집·엑셀 편집·다운로드를 수행하는 것을 목표로 합니다.
- 기관 로그인과 스크래핑은 Pages에서 실행되는 브라우저 스크립트로 가능한지 먼저 확인합니다.
- 직접 수집 가능 여부는 사용자가 확인합니다. 현재 구현 가능 여부를 확정하지 않습니다.
- 사용자는 각자 본인의 기관 계정을 입력합니다.
- 서비스 이용 권한 확인과 기관 계정 연결을 구분한다는 요구사항은 유지합니다.
- 기존에 제안한 작업 중계 API와 외부 실행 환경은 현재 구성에 포함하지 않습니다.

### 이전 직접 연동 점검 기록

2026년 9월 15일 비로그인 상태에서 기관 사이트 첫 화면·홈·발주 목록에 점검용 출처로 GET 요청을 보냈을 때 CORS 허용 헤더가 없었습니다. 실제 Pages에서의 기관 로그인·발주 수집 가능 여부는 사용자의 확인 결과를 기준으로 후속 설계를 정합니다.

## 2. 기존 자료에서 확인한 내용

### 기존 프로그램: `sg_pj-main`

- `package.json`의 실행 진입점과 개발 명령은 `another.js`를 사용합니다.
- 두 기관 **아이니웨딩**(`https://prm.iniwedding.com`)과 **S웨딩**(`https://prm.s-wed.co.kr`)에 순서대로 로그인해 목록과 상세 발주서를 읽습니다.
- 원본은 같은 계정을 두 기관에 사용합니다. 새 화면에서는 기관을 선택하고 기관별로 본인 계정을 입력합니다.
- 공통 요청은 첫 화면 → `/bbs/login_check.php` 로그인 → `/home` 또는 `/home/` → `/Order/OrderList.php` 목록 → `/Order/ContractOptionFax_Fixed.php` 상세 순서입니다.
- 목록 요청의 `SearchMon`은 본식 `WMON` / 촬영 `RMON`, `SDAY`·`EDAY`는 조회 기간이며 `pages`를 증가시켜 목록을 순회합니다.
- 촬영은 목록과 상세 상품명에 `촬영`이 포함된 항목을 대상으로 합니다.
- `index.js`의 example 도메인은 데모이며 실제 기관으로 추가하지 않았습니다. `backup/another1.js`는 아이니 통신 실험 코드이고, `evs.js`는 빈 파일입니다.
- 검색 유형은 리허설·촬영용과 예식일로 구분합니다.
- 시작일과 종료일을 입력받아 엑셀을 생성합니다.
- 코드상 목록 수집은 상태에 `확인`이 포함된 행을 만나면 중단됩니다. 따라서 생성 파일을 전체 발주 목록으로 단정하지 않습니다.
- 배송시간과 본식 부토니에 항목은 빈 값으로 생성됩니다.
- `credentials.js`를 참조하지만 전달된 폴더에는 해당 파일이 없습니다. 이번 분석에서는 프로그램을 실행하거나 실제 로그인하지 않았습니다.

### 입력 예시

`참고/예식일_2026-09-12_to_2026-09-12.xlsx`

| 시트 | 데이터 행 수 | 구조 |
| --- | ---: | --- |
| 아이니 | 37 | 발주코드 등 10개 열 |
| S웨딩 | 5 | 아이니와 같은 열 구조 |

입력 열:

`발주코드 / 담당플래너 / 신부명 / 배송지 / 배송시간 / 발주부케 / 부토니에 / 특이사항(기타사항) / 예식장소 / 예식시간`

이 예시에는 **행별 예식 날짜가 없습니다.** 파일명은 단일 날짜를 나타냅니다. 여러 날짜를 조회한 파일도 같은 구조라면 파일명에 있는 기간만으로 각 행의 날짜를 복원할 수 없습니다.

다시 확인한 `another.js`는 `아이니`, `S웨딩` 두 시트를 생성하며 참고 파일과 일치합니다. 새 화면은 선택한 기관별로 같은 이름의 원본 시트를 생성합니다.

### 목표 예시

`참고/2026_발주체크__0909_0915_v00.01.XLSX`

| 시트 | 데이터 행 수 | 주요 구조 |
| --- | ---: | --- |
| 9.12(토) | 29 | 날짜 제목, 열 제목, 번호를 포함한 본식 발주표 |
| 9.13(일) | 11 | 본식 발주표 |
| 촬영 | 6 | 날짜를 포함한 촬영 발주표 |

행 수는 제목과 빈 서식 행을 제외하고 신부명이 있는 데이터 행을 센 값입니다. 목표 파일에는 수식과 병합 셀이 없으며, A4 가로 인쇄 설정이 있습니다. 표의 색상·글꼴·열 너비·행 높이는 구현 시 별도로 비교해 재현합니다.

### 비교 결과와 해석

- 입력 42행을 담당플래너·신부명·예식장소·예식시간으로 비교하면 29개 그룹이 됩니다. 비교 시 앞뒤 공백과 플래너명의 `-S웨딩` 표시 차이를 정리했습니다.
- 이 29개 그룹은 목표 파일의 `9.12(토)` 29행과 대응합니다.
- 여러 발주를 한 행사 행으로 합치는 작업이 있는 것으로 추정됩니다. 정확한 합산·병합 규칙은 아직 확정되지 않았습니다.
- 일대일로 대응하는 행에서도 부케명, 특이사항, 배송지 등의 변경이 확인됩니다. 원본만으로 모든 수정 내용을 계산할 수 있다고 보장할 수 없습니다.
- 제공된 원본은 9월 12일 예식 자료입니다. 목표 파일의 9월 13일 예식과 촬영 데이터를 재현하려면 해당 원본이나 수동 입력이 추가로 필요합니다.

## 3. 1차 개발 사용 흐름

1. **기관과 계정 입력**
   - 아이니웨딩·S웨딩 중 하나 이상을 선택하고 각 기관의 아이디·비밀번호를 입력합니다.
   - 별도의 계정 사전 검증이나 서비스 로그인 없이 수집을 시작합니다.
   - 입력 필수 여부는 화면에서 확인하고, 실제 기관 로그인 결과는 수집 과정에서 확인합니다.
2. **조회 조건 설정**
   - 본식·예식일 또는 촬영·리허설일을 선택합니다.
   - 기본 기간(6일 전~내일), 오늘, 최근 7일, 직접 지정 중 선택합니다. 기본 날짜는 사용자 브라우저의 현지 날짜로 계산합니다.
   - 확인 완료 발주에서 종료하는 옵션을 해제하면 확인 완료 발주도 수집합니다.
   - 원본의 `확인` 부분 문자열 검사는 `미확인`도 포함할 수 있어 새 코드에서는 미확인을 구분합니다.
3. **수집과 로그 확인**
   - 기관 접속·로그인·목록 페이지·상세 처리·완료 건수를 하단 터미널에 실시간 표시합니다.
   - 수집 중 설정을 잠그고 로딩 아이콘을 표시합니다. 수집 중지와 로그 지우기·자동 스크롤을 지원합니다.
   - 로그인 거절, 세션 문제, HTTP 오류, 30초 시간 초과, 응답 형식 변경, 빈 결과를 구분합니다.
   - 브라우저가 원인을 숨기는 통신 실패는 CORS·쿠키 정책·네트워크 등의 가능성을 안내합니다.
   - 한 기관이 실패하면 다음 선택 기관을 진행합니다. 상세 통신 실패는 해당 기관 수집을 중단하고, 개별 발주서 파싱 실패는 기록한 뒤 다음 발주서를 처리합니다.
4. **원본 엑셀 다운로드**
   - 본식은 `예식일_시작일_to_종료일.xlsx`, 촬영은 `촬영용_시작일_to_종료일.xlsx`로 저장합니다.
   - 배송시간과 본식 부토니에는 원본처럼 빈 값으로 둡니다. 촬영에는 날짜·요일을 포함합니다.
   - 중지·실패 전에 수집한 행은 일부 결과로 다운로드할 수 있습니다. 파일명에 `_일부수집`을 붙이고 `수집현황` 시트에 기관별 완료 여부를 기록합니다.
   - 결과가 0건이면 파일을 생성하지 않습니다.

일반·다크모드는 헤더 버튼으로 전환하고 선택을 저장합니다. 흰색·검은색 바탕과 `#b9e0fd` 포인트, 둥근 패널, 단일 `system-ui` 글꼴을 사용합니다. 외부 폰트를 다운로드하지 않으며 로딩 아이콘 외 애니메이션은 없습니다. 모바일에서는 패널을 세로로 배치합니다.

**후속 작업:** 허가 사용자 접근 제어, 결과 편집, 발주 합치기, 부케명 변환, 수동 행 추가, 참고 발주체크 양식 출력, 기존 엑셀 보조 입력. 아래 변환·출력 규칙은 후속 설계이며 1차 원본 다운로드에 적용되지 않습니다.

## 4. 변환 규칙 초안

아래 규칙은 구현 제안입니다. 실제 업무 규칙으로 검증한 뒤 확정합니다.

| 항목 | 기본 처리 | 사용자 제어 |
| --- | --- | --- |
| 출처 | 수집 사이트·계정 구분·발주코드를 보존하고, 파일 입력은 원본 파일·시트·행 번호도 보존 | 출처 이름 및 표시 방식 변경 |
| 날짜 | 직접 수집은 상세 발주서의 행사 날짜 사용, 보조 파일 입력은 행 날짜 또는 단일 날짜 파일명에서 제안 | 누락 날짜 확인 및 행별 지정 |
| 여러 날짜 파일 | 행별 날짜가 없으면 미확정 표시 | 날짜 지정 후 시트 분류 |
| 본식 발주 합치기 | 출처·날짜·플래너·신부·장소·시간을 이용해 후보 제안 | 원본 발주 목록 확인 후 합치기·분리 |
| 같은 파일 재입력 | 출처·발주코드와 실제 내용을 비교해 중복 또는 변경 후보 표시 | 유지·제외·갱신 선택 |
| 출력 번호 | 본식 시트의 최종 행 순서에 따라 1부터 부여 | 정렬·행 순서 변경 |
| 담당플래너 | 원본 이름 보존 | 출처 접미사 표시 여부 설정 |
| 배송지 | 원본과 `확인필요` 표시 유지 | 실제 배송지 확인 후 수정 |
| 배송시간 | 빈 값 유지 | 직접 입력, 업무 규칙 확정 후 자동 계산 검토 |
| 발주부케 | 원문 보존, 등록된 변환 규칙으로 표시명 제안 | 상품명 매핑·직접 수정·금액 표시 설정 |
| 부토니에 | 입력값 유지, 없으면 빈 값 | 직접 입력 |
| 특이사항 | 출력 열 이름을 `특이사항`으로 정리하고 원문 보존 | 편집 및 여러 발주 메모 합치기 |
| 원본에 없는 행 | 자동 생성하지 않음 | 수동 추가 또는 다른 원본 가져오기 |

같은 신부의 추가금·추가상품 발주는 서로 다른 유효 발주일 수 있습니다. 이름이 같다는 이유만으로 삭제하거나 금액을 버리지 않습니다. 합친 행에도 원본 발주 목록을 연결하고, 배송지·시간 등이 충돌하면 사용자가 값을 선택하게 합니다.

부케의 실제 품종·디자인과 별도로 전달받은 요청은 원본의 상품 등급이나 가격만으로 확정하지 않습니다. 사용자가 관리하는 변환표 또는 직접 입력으로 보완합니다.

편집 데이터는 원본과 구분해 보관하며, 정렬이나 필터를 바꿔도 수정 내용이 다른 행으로 이동하지 않도록 고정 식별자를 사용합니다.

## 5. 엑셀 출력 기본 형식

### 본식: 날짜별 시트

- 시트명 예시: `9.12(토)`
- 첫째 행: 날짜 제목
- 둘째 행: 아래 열 제목
- 셋째 행부터: 데이터

`NO / 담당플래너 / 신부명 / 배송지 / 배송시간 / 발주부케 / 부토니에 / 특이사항 / 예식장소 / 예식시간`

### 촬영: 통합 시트

- 시트명: `촬영`
- 첫째 행: 아래 열 제목
- 둘째 행부터: 날짜순 데이터

`날짜 / 담당플래너 / 신부명 / 배송지 / 배송시간 / 발주부케 / 특이사항 / 리허설장소 / 리허설시간`

### 공통

- 참고 양식의 서식과 A4 가로 인쇄를 기본으로 시작합니다.
- 원본 발주코드는 편집 화면에서 추적할 수 있게 유지하고, 기본 발주체크 출력에서는 제외합니다.
- 긴 특이사항의 줄바꿈과 행 높이를 조절합니다.
- 데이터가 없는 날짜의 시트 생성 여부를 선택할 수 있게 합니다.
- 연도를 넘기는 기간에는 시트명 충돌을 피하고, 파일명에 양쪽 연도가 드러나도록 합니다.
- 다운로드한 파일을 Excel에서 열어 한글, 시간, 줄바꿈, 인쇄 미리보기를 검증합니다.

## 10. 개발 환경 실행

### 설치된 기본 요소

- Vite 8.3.0: 로컬 개발 서버와 정적 배포 파일 생성
- ExcelJS 4.4.0: 엑셀 읽기·쓰기와 서식 처리
- 스크래핑 요청·HTML 분석: 브라우저 fetch·DOMParser 사용
- Playwright 1.63.0: 가상 기관 응답을 사용한 브라우저 검증

엑셀 라이브러리는 다운로드 버튼을 누를 때 지연 로드합니다. 계정 입력과 로그 화면은 먼저 사용할 수 있습니다.

### 실행 명령

Node.js는 `20.19 이상인 20.x` 또는 `22.12 이상`이 필요합니다. 구성 시 사용한 버전은 Node.js 22.22.0, npm 10.9.4입니다. [Vite 설치 안내](https://vite.dev/guide/)

```sh
npm ci
npm run dev
```

이미 의존성을 설치한 현재 작업 폴더에서는 `npm run dev`만 실행하면 됩니다. 터미널에 표시되는 로컬 주소로 접속합니다.

```sh
npm run build
npm run preview
```

빌드 결과는 `dist/`에 생성됩니다. GitHub Pages에는 이 폴더의 결과물을 배포합니다. 현재 배포 자동화나 실제 사이트 공개는 수행하지 않았습니다.

`base: './'`을 사용해 저장소 하위 경로에서도 정적 자산을 읽을 수 있게 했습니다. 실제 배포 경로와 라우팅이 정해지면 다시 검증합니다. 개발 서버는 로컬 주소에 바인딩하며 외부 사이트를 중계하는 프록시는 설정하지 않았습니다.

### 자동 검증

```sh
npx playwright install chromium
npm test
```

`npm test`는 빌드 후 로컬 미리보기 서버(4188 포트)에서 가상 응답으로 Chromium 테스트를 실행합니다. 테스트 결과와 화면 캡처는 `test-results/`에 생성되며 Git 추적에서 제외합니다.

빌드 시 ExcelJS 단일 청크가 약 930kB(압축 전)여서 크기 경고가 표시됩니다. 다운로드 시 지연 로드하며, 빌드 실패는 아닙니다.

### 설치 검사 결과

2026년 9월 15일 `npm audit`에서 `uuid < 11.1.1`과 이를 사용하는 ExcelJS에 대해 보통 등급 경고 2건이 보고됐습니다. 같은 하위 의존성 문제의 영향 관계이며, 설치와 빌드는 정상 완료했습니다. 일부 하위 패키지의 지원 종료 경고도 있습니다.

자동 수정 제안은 ExcelJS를 3.4.0으로 낮추는 주요 버전 변경이므로 적용하지 않았습니다. 이 의존성 경고는 남아 있으며, 수정 버전 또는 대체 라이브러리 적용은 별도로 검토합니다. [uuid 관련 보안 공지](https://github.com/advisories/GHSA-w5hq-g745-h8pq)

## 11. 계정 처리와 후속 서비스 인증

이번 1차는 사용자 요청에 따라 별도 사전 계정 검증 버튼을 두지 않습니다. 수집을 시작하면 기관 로그인 요청부터 진행하고 실패 원인을 로그에 표시합니다. HTTP 200만으로 성공을 판단하지 않으며 로그인 응답과 홈 제목을 확인합니다.

- 기관별 본인 계정을 입력하고 선택한 기관만 수집합니다.
- 수집 중 입력을 잠그고 종료·실패·중지 시 선택한 기관의 비밀번호 입력값과 수집용 계정 객체를 정리합니다.
- 앱은 아이디·비밀번호를 localStorage나 sessionStorage에 저장하지 않습니다. localStorage에는 테마 선택만 저장합니다.
- 비밀번호·아이디는 로그에서 숨기고, 기관 응답 HTML을 로그에 그대로 노출하지 않습니다.
- 수집 결과는 화면 메모리에만 있으며 새로고침하면 사라집니다.
- 기관 세션 쿠키는 브라우저와 기관이 관리합니다. 수집 중지는 기관 원격 로그아웃을 의미하지 않습니다.

허가 사용자 접근 제한, 기관 연결 완료 표시·연결 해제, 원격 로그아웃은 후속 범위입니다. 현재 화면에는 서비스 접근 제한이 구현되어 있지 않으며 공개 프론트엔드 환경 변수나 화면상 비밀번호 비교를 접근 통제로 간주하지 않습니다.
