#  발주체크 웹 도구

기존 EXE의 로그인·발주 조회·상세 수집·엑셀 생성 기능 전체를 정적 웹페이지로 옮기고, 수집한 자료를 날짜별 발주체크표로 정리·편집·다운로드하는 프로젝트입니다.

GitHub Pages 배포를 목표로 합니다. Vite 기반 개발 환경, 초기 화면, ExcelJS 설치를 완료했습니다. 로그인·수집·발주체크 변환 기능은 아직 구현하지 않았습니다.

## 1. 필수 요구사항과 구현 조건

**첫 버전부터 EXE에서 수행하던 로그인·발주 조회·상세 수집·원본 엑셀 생성 전체를 정적 웹페이지에서 처리해야 합니다.** 이어서 발주체크표 자동 정리·사용자 편집·다운로드를 제공합니다.

사용자는 GitHub Pages에 접속해 모든 작업을 수행합니다. 별도 EXE 실행과 사전 엑셀 생성은 필수 사용 흐름에 포함하지 않습니다. 기존 엑셀 불러오기는 보조 기능입니다.

### 필수 기능

| 기능 | 목표 |
| --- | --- |
| 로그인·세션 관리 | 사용자가 입력한 계정으로 대상 사이트에 로그인하고 조회 중 인증 유지 |
| 검색 조건 | 리허설·촬영용 또는 예식일, 시작일·종료일 지정 |
| 목록 수집 | 페이지를 순회하고 기존 수집 조건에 맞는 발주 추출 |
| 상세 수집 | 각 발주서의 항목과 행사 날짜·시간 추출 |
| 원본 엑셀 생성 | 기존 EXE에 해당하는 원본 엑셀 다운로드 |
| 발주체크표 생성 | 수집 결과를 정리·편집해 최종 엑셀 다운로드 |
| 오류 처리 | 로그인 실패·세션 만료·수집 실패·빈 결과를 구분하고 진행 상황 표시 |

### 현재 판단: 정적 페이지의 직접 연동 조건이 충족되지 않음

GitHub Pages는 HTML·CSS·JavaScript를 제공하는 정적 호스팅입니다. 기존 Node.js 프로그램을 서버에서 실행하는 기능은 제공하지 않으며, 수집 요청은 사용자 브라우저에서 대상 사이트로 직접 보내야 합니다. [GitHub Pages 공식 문서](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

2026년 9월 15일, 로그인 없이 다음 주소에 GET 요청을 보내 응답 헤더를 확인했습니다. 점검용 요청 출처는 `https://example.github.io`입니다.

| 요청 주소 | 관측 결과 |
| --- | --- |
| `https://prm.iniwedding.com/` | CORS 허용 헤더 없음 |
| `https://prm.iniwedding.com/home` | `/home/`으로 이동 후 CORS 허용 헤더 없음 |
| `https://prm.iniwedding.com/Order/OrderList.php` | CORS 허용 헤더 없음 |

세 최종 응답은 HTTP 200이었지만 `Access-Control-Allow-Origin`과 `Access-Control-Allow-Credentials`가 없었습니다. 따라서 **확인한 응답은 다른 출처의 브라우저 JavaScript에서 읽을 수 없습니다.** HTTP 200은 로그인이나 발주 조회 성공을 뜻하지 않습니다. 실제 배포 출처와 인증 후 응답은 아직 검증하지 않았으므로, 모든 연동 경로가 불가능하다고 확정한 것은 아닙니다. [MDN CORS 문서](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)

기존 Node.js 코드의 쿠키 저장소와 `Origin` 헤더 지정도 그대로 옮길 수 없습니다. 일반 웹페이지는 `Cookie`와 `Origin` 요청 헤더를 임의로 지정할 수 없으며, 브라우저가 인증 쿠키를 관리합니다. [MDN 요청 헤더 제약](https://developer.mozilla.org/en-US/docs/Glossary/Forbidden_request_header)

`fetch(..., { mode: "no-cors" })`로 요청해도 응답 내용을 읽을 수 없어 발주 HTML 분석에 사용할 수 없습니다. [MDN 요청 모드 문서](https://developer.mozilla.org/en-US/docs/Web/API/Request/mode)

### 정적 페이지만으로 구현하기 위한 선행 조건

- 대상 사이트가 실제 배포 출처의 로그인·조회 응답 읽기를 허용하거나, 동등한 기능의 브라우저 연동 API를 제공해야 합니다.
- 쿠키 인증을 유지한다면 명시적인 출처 허용과 자격 증명 허용, 교차 사이트 쿠키 정책까지 함께 충족해야 합니다. CORS 허용만으로 인증 성공을 보장하지 않습니다.
- 대상 사이트의 로그인, 세션 유지, 목록·상세 조회가 지원 브라우저에서 실제 동작하는지 확인해야 합니다.

대상 사이트를 변경할 수 없고 허용된 연동 경로도 없다면, **GitHub Pages의 정적 파일만으로 현재 EXE 전체를 대체할 수 없습니다.** 이 경우 별도 백엔드나 브라우저 확장 등 추가 구성에 대한 요구사항 변경이 필요합니다. 이들은 현재 확정된 구성에 포함하지 않습니다.

직접 연동 가능 여부를 첫 개발 단계에서 검증합니다. 엑셀 업로드 기능만으로 EXE 대체가 완료되었다고 판단하지 않습니다.

## 2. 기존 자료에서 확인한 내용

### 기존 프로그램: `sg_pj-main`

- `package.json`의 실행 진입점과 개발 명령은 `another.js`를 사용합니다.
- 외부 발주 사이트에 로그인한 뒤 목록과 상세 발주서를 읽습니다.
- 검색 유형은 리허설·촬영용과 예식일로 구분합니다.
- 시작일과 종료일을 입력받아 엑셀을 생성합니다.
- 코드상 목록 수집은 상태에 `확인`이 포함된 행을 만나면 중단됩니다. 따라서 생성 파일을 전체 발주 목록으로 단정하지 않습니다.
- 배송시간과 본식 부토니에 항목은 빈 값으로 생성됩니다.
- `credentials.js`를 참조하지만 전달된 폴더에는 해당 파일이 없습니다. 이번 분석에서는 프로그램을 실행하거나 실제 로그인하지 않았습니다.

### 입력 예시

`참고/예식일_2026-09-12_to_2026-09-12.xlsx`

| 시트 | 데이터 행 수 | 구조 |
| --- | ---: | --- |
| 아이니 | 37 | 발주코드 등 10개 열 |
| S웨딩 | 5 | 아이니와 같은 열 구조 |

입력 열:

`발주코드 / 담당플래너 / 신부명 / 배송지 / 배송시간 / 발주부케 / 부토니에 / 특이사항(기타사항) / 예식장소 / 예식시간`

이 예시에는 **행별 예식 날짜가 없습니다.** 파일명은 단일 날짜를 나타냅니다. 여러 날짜를 조회한 파일도 같은 구조라면 파일명에 있는 기간만으로 각 행의 날짜를 복원할 수 없습니다.

전달된 코드의 출력 시트명은 `Sheet 1`이지만 참고 파일에는 `아이니`, `S웨딩`이 있습니다. 시트 분리 과정은 현재 코드만으로 설명되지 않으므로, 가져오기 기능은 특정 시트명을 고정하지 않고 열 이름을 기준으로 판별해야 합니다.

### 목표 예시

`참고/2026_발주체크__0909_0915_v00.01.XLSX`

| 시트 | 데이터 행 수 | 주요 구조 |
| --- | ---: | --- |
| 9.12(토) | 29 | 날짜 제목, 열 제목, 번호를 포함한 본식 발주표 |
| 9.13(일) | 11 | 본식 발주표 |
| 촬영 | 6 | 날짜를 포함한 촬영 발주표 |

행 수는 제목과 빈 서식 행을 제외하고 신부명이 있는 데이터 행을 센 값입니다. 목표 파일에는 수식과 병합 셀이 없으며, A4 가로 인쇄 설정이 있습니다. 표의 색상·글꼴·열 너비·행 높이는 구현 시 별도로 비교해 재현합니다.

### 비교 결과와 해석

- 입력 42행을 담당플래너·신부명·예식장소·예식시간으로 비교하면 29개 그룹이 됩니다. 비교 시 앞뒤 공백과 플래너명의 `-S웨딩` 표시 차이를 정리했습니다.
- 이 29개 그룹은 목표 파일의 `9.12(토)` 29행과 대응합니다.
- 여러 발주를 한 행사 행으로 합치는 작업이 있는 것으로 추정됩니다. 정확한 합산·병합 규칙은 아직 확정되지 않았습니다.
- 일대일로 대응하는 행에서도 부케명, 특이사항, 배송지 등의 변경이 확인됩니다. 원본만으로 모든 수정 내용을 계산할 수 있다고 보장할 수 없습니다.
- 제공된 원본은 9월 12일 예식 자료입니다. 목표 파일의 9월 13일 예식과 촬영 데이터를 재현하려면 해당 원본이나 수동 입력이 추가로 필요합니다.

## 3. 목표 사용 흐름

1. **사이트 접속과 로그인**
   - GitHub Pages의 웹 화면에서 대상 사이트 계정으로 로그인합니다.
   - 로그인 결과와 세션 만료 여부를 표시합니다.
   - 계정 비밀번호는 코드·저장소·브라우저 영구 저장소에 보관하지 않습니다.
2. **조회 조건 설정과 수집**
   - 본식 또는 촬영, 시작일과 종료일을 선택합니다.
   - 발주 목록의 페이지를 순회하고 각 상세 발주서를 수집합니다.
   - 수집 진행 상황과 실패 항목을 표시합니다.
   - 행사 날짜는 상세 자료에서 확보하고 누락 시 사용자 확인을 받습니다.
3. **수집 결과 확인과 자동 정리**
   - 기존 EXE에 해당하는 원본 엑셀을 필요에 따라 다운로드합니다.
   - 수집 결과에서 발주 합치기 후보와 부케명 변환 규칙을 검토합니다.
   - 기존 엑셀을 보조 입력으로 추가할 수도 있게 합니다.
4. **미리보기에서 편집**
   - 날짜·출처·배송지 등으로 필터링하고 행 순서를 정합니다.
   - 배송지, 배송시간, 부케명, 부토니에, 특이사항 등을 수정합니다.
   - 행을 추가하거나 출력에서 제외하고, 합친 행을 다시 나눌 수 있게 합니다.
5. **출력 설정과 다운로드**
   - 포함할 시트, 표시 열, 정렬, 글자 크기, 열 너비와 인쇄 방향을 선택합니다.
   - 미확인 날짜와 충돌 항목을 확인한 뒤 발주체크 엑셀을 생성합니다.
   - 연도, 기간, 업체명, 버전 표기는 사용자가 변경할 수 있게 합니다.

## 4. 변환 규칙 초안

아래 규칙은 구현 제안입니다. 실제 업무 규칙으로 검증한 뒤 확정합니다.

| 항목 | 기본 처리 | 사용자 제어 |
| --- | --- | --- |
| 출처 | 수집 사이트·계정 구분·발주코드를 보존하고, 파일 입력은 원본 파일·시트·행 번호도 보존 | 출처 이름 및 표시 방식 변경 |
| 날짜 | 직접 수집은 상세 발주서의 행사 날짜 사용, 보조 파일 입력은 행 날짜 또는 단일 날짜 파일명에서 제안 | 누락 날짜 확인 및 행별 지정 |
| 여러 날짜 파일 | 행별 날짜가 없으면 미확정 표시 | 날짜 지정 후 시트 분류 |
| 본식 발주 합치기 | 출처·날짜·플래너·신부·장소·시간을 이용해 후보 제안 | 원본 발주 목록 확인 후 합치기·분리 |
| 같은 파일 재입력 | 출처·발주코드와 실제 내용을 비교해 중복 또는 변경 후보 표시 | 유지·제외·갱신 선택 |
| 출력 번호 | 본식 시트의 최종 행 순서에 따라 1부터 부여 | 정렬·행 순서 변경 |
| 담당플래너 | 원본 이름 보존 | 출처 접미사 표시 여부 설정 |
| 배송지 | 원본과 `확인필요` 표시 유지 | 실제 배송지 확인 후 수정 |
| 배송시간 | 빈 값 유지 | 직접 입력, 업무 규칙 확정 후 자동 계산 검토 |
| 발주부케 | 원문 보존, 등록된 변환 규칙으로 표시명 제안 | 상품명 매핑·직접 수정·금액 표시 설정 |
| 부토니에 | 입력값 유지, 없으면 빈 값 | 직접 입력 |
| 특이사항 | 출력 열 이름을 `특이사항`으로 정리하고 원문 보존 | 편집 및 여러 발주 메모 합치기 |
| 원본에 없는 행 | 자동 생성하지 않음 | 수동 추가 또는 다른 원본 가져오기 |

같은 신부의 추가금·추가상품 발주는 서로 다른 유효 발주일 수 있습니다. 이름이 같다는 이유만으로 삭제하거나 금액을 버리지 않습니다. 합친 행에도 원본 발주 목록을 연결하고, 배송지·시간 등이 충돌하면 사용자가 값을 선택하게 합니다.

부케의 실제 품종·디자인과 별도로 전달받은 요청은 원본의 상품 등급이나 가격만으로 확정하지 않습니다. 사용자가 관리하는 변환표 또는 직접 입력으로 보완합니다.

편집 데이터는 원본과 구분해 보관하며, 정렬이나 필터를 바꿔도 수정 내용이 다른 행으로 이동하지 않도록 고정 식별자를 사용합니다.

## 5. 엑셀 출력 기본 형식

### 본식: 날짜별 시트

- 시트명 예시: `9.12(토)`
- 첫째 행: 날짜 제목
- 둘째 행: 아래 열 제목
- 셋째 행부터: 데이터

`NO / 담당플래너 / 신부명 / 배송지 / 배송시간 / 발주부케 / 부토니에 / 특이사항 / 예식장소 / 예식시간`

### 촬영: 통합 시트

- 시트명: `촬영`
- 첫째 행: 아래 열 제목
- 둘째 행부터: 날짜순 데이터

### 공통

- 참고 양식의 서식과 A4 가로 인쇄를 기본으로 시작합니다.
- 원본 발주코드는 편집 화면에서 추적할 수 있게 유지하고, 기본 발주체크 출력에서는 제외합니다.
- 긴 특이사항의 줄바꿈과 행 높이를 조절합니다.
- 데이터가 없는 날짜의 시트 생성 여부를 선택할 수 있게 합니다.
- 연도를 넘기는 기간에는 시트명 충돌을 피하고, 파일명에 양쪽 연도가 드러나도록 합니다.
- 다운로드한 파일을 Excel에서 열어 한글, 시간, 줄바꿈, 인쇄 미리보기를 검증합니다.

## 6. 기술 구성 제안

| 영역 | 제안 |
| --- | --- |
| 화면 | HTML·CSS·JavaScript 기반의 정적 웹 앱, Vite 8.3.0 개발·빌드 환경 |
| 로그인·수집 | 브라우저에서 대상 사이트로 직접 요청, CORS·인증 조건 충족 여부가 선행 조건 |
| HTML 분석 | 브라우저의 DOMParser 등으로 응답 분석, 외부 HTML을 화면에 직접 실행하지 않음 |
| 엑셀 처리 | ExcelJS 4.4.0 설치 완료, 실제 참고 양식과 브라우저 호환성은 구현 시 검증 |
| 배포 | GitHub Pages |
| 데이터 처리 | 사용자 브라우저 메모리에서 수행 |
| 설정 보관 | 개인정보가 없는 변환 규칙·출력 설정만 선택적으로 브라우저에 저장 |
| 작업 이어하기 | 후속 기능으로 작업 파일 내보내기·다시 불러오기 검토 |

ExcelJS는 브라우저용 워크북 처리와 XLSX 읽기·쓰기, 서식 및 인쇄 설정을 문서화하고 있습니다. 설치 버전은 package.json과 package-lock.json에 고정하며, 참고 양식과의 실제 호환성은 후속 구현에서 검증합니다. [ExcelJS 공식 문서](https://github.com/exceljs/exceljs#browser)

한 번만 쓰는 짧은 로직은 인라인으로 작성합니다. 재사용이 필요하거나 분기·예외 처리 때문에 흐름이 복잡해질 때만 함수를 분리하고, 초기부터 불필요하게 많은 모듈을 만들지 않습니다.

## 7. 파일과 배포 관리

현재 위치를 새 프로젝트의 루트로 사용하고, 기존 자료는 분석용으로 보관합니다. 개발 환경과 초기 화면을 다음과 같이 구성했습니다.

```text
ganadara/
├── README.md          # 프로젝트 설명과 설계
├── package.json       # 의존성과 실행 명령
├── package-lock.json  # 설치 버전 고정
├── vite.config.js     # 정적 빌드·로컬 서버 설정
├── .gitignore         # 의존성·계정·참고 자료 제외
├── index.html         # 한국어 초기 화면
├── src/
│   ├── main.js        # 화면 진입점
│   └── style.css      # 기본 스타일
├── dist/              # 빌드 시 생성되는 배포 파일
├── sg_pj-main/        # 기존 프로그램
└── 참고/              # 로컬 분석용 원본과 목표 파일
```

실제 발주 파일에는 신부명과 행사 정보가 있으므로 공개 저장소·배포 파일에 포함하지 않습니다. 배포 구성 시 기존 프로그램, 계정 파일, 참고 엑셀, 작업 파일을 제외하고 웹 앱에 필요한 파일만 배포합니다. 공개 테스트에는 가상 데이터를 사용합니다.

직접 연동이 가능한 경우 로그인·조회 요청은 대상 사이트에만 보내고, 수집 결과의 편집·엑셀 생성은 브라우저에서 처리합니다. 비밀번호·세션 값은 로그와 작업 파일에 포함하지 않습니다. 보조 입력으로 선택한 엑셀 내용은 서버로 전송하지 않는 구조로 구현합니다. 새로고침 시 편집 내용이 사라질 수 있으므로 다운로드 전 화면에서 안내하고, 작업 저장 기능은 별도로 설계합니다.

## 10. 개발 환경 실행

### 설치된 기본 요소

- Vite 8.3.0: 로컬 개발 서버와 정적 배포 파일 생성
- ExcelJS 4.4.0: 엑셀 읽기·쓰기와 서식 처리
- 요청·HTML 분석: 브라우저 기본 `fetch`와 `DOMParser` 사용 예정

기존 EXE의 Node.js 전용 쿠키 저장소·실행 파일 패키징 도구는 새 웹 프로젝트에 설치하지 않았습니다. 스크래핑도 브라우저에서 실행하면 1절의 CORS·인증 조건을 충족해야 합니다.

### 실행 명령

Node.js는 `20.19 이상인 20.x` 또는 `22.12 이상`이 필요합니다. 구성 시 사용한 버전은 Node.js 22.22.0, npm 10.9.4입니다. [Vite 설치 안내](https://vite.dev/guide/)

```sh
npm ci
npm run dev
```

이미 의존성을 설치한 현재 작업 폴더에서는 `npm run dev`만 실행하면 됩니다. 터미널에 표시되는 로컬 주소로 접속합니다.

```sh
npm run build
npm run preview
```

빌드 결과는 `dist/`에 생성됩니다. GitHub Pages에는 이 폴더의 결과물을 배포합니다. 현재 배포 자동화나 실제 사이트 공개는 수행하지 않았습니다.

`base: './'`을 사용해 저장소 하위 경로에서도 정적 자산을 읽을 수 있게 했습니다. 실제 배포 경로와 라우팅이 정해지면 다시 검증합니다. 개발 서버는 로컬 주소에 바인딩하며 외부 사이트를 중계하는 프록시는 설정하지 않았습니다.
